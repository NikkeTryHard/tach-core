# Architectural Specification: Project Tach
## Linux Core and Compatibility Layer

### 1. Architectural Principles and System Overview

The design of Project Tach's "Linux Core" compatibility layer addresses a fundamental tension in modern software testing: the dichotomy between execution speed and environmental isolation. Traditional virtualization methods, such as Virtual Machines (VMs) or heavy containers like Docker, offer robust isolation but incur startup latencies and resource overheads that are unacceptable for high-frequency integration testing. Conversely, running tests directly on the host operating system maximizes performance but risks environment pollution, dependency conflicts, and non-deterministic failures. Project Tach aims to bridge this gap by engineering a hybrid runtime environment that leverages OS-specific primitives—Linux Namespaces, Windows NT API cloning, and macOS Mach VM remapping—to deliver sub-millisecond isolation with near-native performance.

This architectural blueprint details the implementation of a high-performance filesystem virtualization layer, a zero-overhead legacy plugin system via PyO3, and a transactional database isolation mechanism. Furthermore, it explores the frontiers of runtime security through eBPF syscall rewriting and Library OS integration. The rigorous analysis of these components demonstrates that a "process-based" virtualization strategy, augmented by kernel-level filtering and copy-on-write memory semantics, provides the optimal balance for the next generation of test execution infrastructure.

#### 1.1. Core Design Philosophy: The Process as the Container

The central tenet of the proposed architecture is treating the process, rather than the machine, as the unit of isolation. By manipulating the view of system resources—files, memory, and network interfaces—available to a single process tree, Project Tach avoids the overhead of hardware virtualization. This approach requires deep integration with the kernel's virtual memory manager (VMM) and virtual filesystem (VFS) layers.

On Linux, this is achieved natively through Namespaces. On Windows and macOS, where such uniform primitives are absent or restricted, the architecture employs a strategy of "emulated forking" and user-space interposition. This necessitates a modular design where the "Linux Core" serves as the reference implementation, while platform-specific adapters translate abstract isolation requests into the nearest available OS primitive—be it NtCreateUserProcess on Windows or vm_remap on macOS.

### 2. High-Performance Filesystem Virtualization

Filesystem virtualization is the linchpin of the Project Tach architecture. The ability to present a clean, consistent, and disposable filesystem view to each test execution context allows for the safe parallelization of I/O-heavy workloads. Three distinct mechanisms were evaluated for this purpose: User-Space Interposition (LD_PRELOAD), Kernel-Space Filtering (seccomp-bpf), and Native Namespace Isolation.

#### 2.1. Mechanism 1: User-Space Interposition (LD_PRELOAD)

The most traditional method for intercepting filesystem calls in user space on Unix-like systems is the LD_PRELOAD technique. This mechanism relies on the dynamic linker's behavior to load specified shared libraries before any others, allowing the injected library to hook and override symbols from libc, such as open, write, and stat.¹

##### 2.1.1. Technical Implementation and Limitations

In the context of Project Tach, an LD_PRELOAD agent would function by wrapping libc calls. When a test process attempts to open a file (e.g., /etc/config), the wrapper intercepts this call, checks a configuration map, and redirects the path to a sandboxed location (e.g., /tmp/tach_sandbox_1/config) before calling the real dlsym(RTLD_NEXT, "open").³

While conceptually simple, this approach suffers from significant fragility in modern polyglot environments. The primary limitation is its dependency on the dynamic linker. Statically linked binaries—common in the Go and Rust ecosystems—do not use the dynamic linker and thus completely bypass LD_PRELOAD hooks. Furthermore, applications that invoke system calls directly via inline assembly (a technique often used for performance optimization in cryptographic libraries or by malicious code) will evade interception entirely.¹

##### 2.1.2. Security and Consistency Implications

Security presents another major drawback. LD_PRELOAD offers no true isolation boundary; it is merely a redirection layer. A malicious or poorly written test plugin can easily bypass the shim by unsetting the LD_PRELOAD environment variable for child processes or using syscall() directly. Additionally, maintaining consistency between the shim's internal state and the kernel's actual filesystem state is complex. Race conditions can occur if the shim updates its mapping table while a highly concurrent test suite is spawning threads, leading to "leakage" where writes accidentally touch the host filesystem.¹

Despite these flaws, LD_PRELOAD remains relevant for specific use cases within Project Tach, particularly for "soft" virtualization tasks like caching standard library calls or mocking time functions, where security is not the primary concern but performance is paramount.

#### 2.2. Mechanism 2: Kernel-Space Trap-and-Emulate (Seccomp-BPF)

To overcome the bypass issues of user-space hooking, the architecture evaluates kernel-level interception using Secure Computing mode extended with Berkeley Packet Filter (seccomp-bpf). This mechanism allows the definition of a syscall filter policy that is enforced by the kernel itself, irrespective of how the syscall was invoked (libc or assembly).

##### 2.2.1. The Performance of Filtering vs. Tracing

Historically, system call interception was performed using ptrace, the mechanism behind debuggers like GDB and strace. However, ptrace imposes a severe performance penalty due to the context switching required. Every intercepted syscall forces the tracee to stop, the kernel to signal the tracer (context switch 1), the tracer to run and inspect the state, and then restart the tracee (context switch 2).¹ Research benchmarks indicate that ptrace can impose overheads exceeding 110% on parallel compilation workloads.¹

Seccomp-BPF significantly mitigates this by moving the filtering logic *into the kernel*. A BPF program loaded by the runner inspects syscall arguments. If the syscall matches a permitted pattern (e.g., read on an already-open file descriptor), it is allowed to proceed immediately without triggering a context switch to user space. This can reduce the overhead of interposition from >100% to approximately 45% for heavy workloads, and significantly lower for I/O-bound tasks where many calls are "allowed" by default.¹

##### 2.2.2. Syscall Reduction Strategy

A key insight from the analysis of the MBOX system is the ability of seccomp-bpf to reduce the surface area of interception. In a typical untar benchmark, which generates 543k system calls, over 60% are read and write operations on established file descriptors. By configuring the BPF filter to ignore these safe operations and only trap open, rename, or execve, the number of interposed events can be reduced by nearly 85%.¹

However, seccomp-bpf essentially turns the Linux kernel into a microkernel-like environment where the filesystem is implemented in user space (via the tracer). This "trap-and-emulate" model still incurs overhead for every metadata operation (stat, open), which can be a bottleneck for Python applications that perform extensive module searching on startup.⁷

#### 2.3. Mechanism 3: Native Isolation (Linux Namespaces)

The superior solution for Project Tach's filesystem virtualization is the use of Linux Namespaces, specifically the Mount (CLONE_NEWNS) and User (CLONE_NEWUSER) namespaces. This approach leverages the kernel's native VFS structures to provide isolation, eliminating the per-syscall overhead of interception.

##### 2.3.1. Implementation via Unshare and Bind Mounts

The architecture employs unshare(CLONE_NEWUSER | CLONE_NEWNS) to create a private mount namespace. Crucially, the User namespace allows a non-root process to map its user ID to root (0) *inside* the namespace. This grants the process the capability to perform mount operations—such as mount --bind—without requiring actual root privileges on the host.⁸

Once inside the namespace, the runner constructs the virtual filesystem topology using bind mounts. For example, to inject a virtual configuration file, the runner binds a temporary file over /etc/config. To sandbox writes, it mounts an OverlayFS or a temporary directory over the application's workspace. Finally, pivot_root moves the root of the namespace to this constructed environment, rendering the host's actual root inaccessible.⁸

##### 2.3.2. Performance Superiority

The performance advantage of Namespaces is decisive. Once the namespace is established (a process taking milliseconds), filesystem operations run at native speed. The kernel resolves paths using the namespace-specific vfsmount table. There are no context switches to a tracer, no BPF evaluation overhead for file access, and no fragility regarding static binaries.¹

#### 2.4. Comparative Architectural Analysis

The following table summarizes the trade-offs determining the selection of Namespaces as the primary mechanism for the "Linux Core":

| Feature Category | User-Space (LD_PRELOAD) | Trap-and-Emulate (Seccomp-BPF) | Native Isolation (Namespaces) |
| :--- | :--- | :--- | :--- |
| **Performance Overhead** | Low (< 5%) for hooked calls | High (~15-45%) due to traps | Negligible (Native Kernel Speed) |
| **Isolation Strength** | Weak (Bypassable) | Strong (Kernel Enforced) | Strongest (Kernel Enforced) |
| **Binary Compatibility** | Dynamic linked only | All (including Static/Go) | All Binaries |
| **Implementation Complexity** | High (Reimplementing libc) | High (Syscall Emulation) | Medium (Mount Topology) |
| **Privilege Requirement** | None | None (with User NS) | None (with User NS) |
| **Concurrency Impact** | Race conditions in wrapper | Serialization of trapped calls | Fully Concurrent |

**Architectural Decision:** Project Tach will utilize a **Namespace-First** architecture. The runner will attempt to unshare the User and Mount namespaces. If this fails (e.g., inside a restricted container), it will fall back to **Seccomp-BPF** with SECCOMP_RET_USER_NOTIF (on modern kernels) or ptrace (as a last resort), accepting the performance penalty. LD_PRELOAD is relegated to auxiliary tasks such as time dilation or fault injection, rather than core isolation.

### 3. Legacy Interoperability: The Rust-Python Bridge via PyO3

While the core runtime of Project Tach is engineered in Rust for performance and safety, the reality of the testing ecosystem necessitates first-class support for Python plugins and legacy test suites. The integration layer must support the execution of existing Python code without the massive serialization overheads typically associated with inter-process communication (IPC).

#### 3.1. PyO3 Integration and Lifecycle Management

PyO3 provides the bindings to embed the CPython interpreter directly into the Rust process. This "Embedding" architecture is distinct from "Extending"; Tach acts as the host executable, managing the Python lifecycle.¹⁰

##### 3.1.1. Embedding CPython

By linking against libpython, Tach creates a Python runtime environment within its own address space. This allows for extremely low-latency function calls between Rust and Python, as they share the same memory space. The initialization phase involves setting up the Python sys.path to include the plugin directories and pre-loading essential modules.

##### 3.1.2. Managing the Global Interpreter Lock (GIL)

A critical challenge in this hybrid architecture is the Global Interpreter Lock (GIL). Rust's concurrency model allows true parallelism, but CPython restricts bytecode execution to a single thread. To prevent the Python runtime from becoming a bottleneck for the entire test runner, Tach employs a strict GIL discipline:

*   **Release Early:** Rust threads acquire the GIL only to marshal data or invoke a Python function.
*   **Allow Threads:** During long-running Rust operations (e.g., file I/O, network requests, or heavy computation), the Python::allow_threads macro is used to release the GIL, allowing other Python threads (or other Rust threads needing the GIL) to proceed.¹¹
*   **Thread Pools:** Tach maintains a dedicated thread pool for Python execution. This segregates GIL-bound tasks from the high-throughput async Rust tasks (Tokio runtime), preventing lock contention from stalling the core event loop.

#### 3.2. Zero-Copy Data Transport Architecture

Legacy IPC methods often rely on pickle, Python's serialization format. pickle is notoriously slow and CPU-intensive, effectively negating the performance benefits of a Rust core if large datasets (like database rows or test vectors) must be passed back and forth.¹²

##### 3.2.1. The Apache Arrow Solution

To achieve high-performance interoperability, Project Tach adopts the **Apache Arrow** memory format. Arrow defines a language-independent columnar memory layout.

*   **Mechanism:** Rust allocates data (e.g., a table of test results) in an Arrow RecordBatch. Because the memory layout is standardized, this memory region can be exposed to Python via pyarrow (the Python bindings for Arrow) *without copying the data*.
*   **Benefits:** This "Zero-Copy" approach reduces the overhead of data transfer from $O(N)$ (serialization) to $O(1)$ (pointer passing). Python code can then manipulate this data using pandas or numpy with native performance.¹⁴

##### 3.2.2. Shared Memory for Large Objects

For scenarios where Arrow is not suitable (e.g., unstructured binary blobs), the architecture utilizes multiprocessing.shared_memory (available in Python 3.8+). Rust creates a POSIX shared memory segment (shm_open) and passes the file descriptor or name to Python. Python wraps this segment in a memoryview, allowing direct read/write access to the underlying buffer. Benchmarks show this is significantly faster than piping pickled objects, especially for image data or large tensors.¹⁵

#### 3.3. State Management and "Hot Reloading"

A significant overhead in running Python tests is the startup time of the interpreter. Restarting the process for every test ensures isolation but destroys performance. Tach implements a "Hot Reloading" strategy to cleanse the environment between tests without process restarts.

##### 3.3.1. Sys.modules Scrubbing

Python caches imported modules in the sys.modules dictionary. To reset the state, Tach takes a snapshot of sys.modules keys after the initial bootstrap. After each test run, the runner iterates through sys.modules and unloads (deletes) any modules that were imported during the test execution. This forces the next test to re-import its dependencies, ensuring that side effects (like modified module-level variables) do not leak.¹⁷

##### 3.3.2. Global Variable Reset

Global variables in Python plugins persist within the process. Tach addresses this by injecting a pytest fixture with autouse=True. This fixture captures the state of the globals() dictionary of the test module during the setup phase and restores it during teardown. This mimics the isolation of a fresh process while retaining the JIT-compiled bytecode and initialized interpreter state.¹⁹

### 4. Database Isolation: Transactional Savepoint Injection

Database tests are the single largest source of latency in integration testing suites. The traditional pattern of DROP DATABASE / CREATE DATABASE is prohibitively expensive (seconds per test). Even TRUNCATE operations incur disk I/O cost (WAL logs). Project Tach implements a "Transaction VCR" strategy using Savepoint Injection.

#### 4.1. The Savepoint Architecture

The core concept is to wrap the entire execution of a test case within a single database transaction, utilizing SQL SAVEPOINTs to create a restore point.

1.  **Connection Setup:** The runner establishes a connection to the database.
2.  **Global Fixture:** Any expensive setup (schema creation, static data loading) runs once and commits.
3.  **Test Wrapper Start:** Before the test logic executes, Tach injects `BEGIN; SAVEPOINT tach_test_start;`.
4.  **Test Execution:** The test runs, performing INSERT, UPDATE, and DELETE operations. To the test, these changes appear permanent and visible.
5.  **Test Wrapper End:** Regardless of success or failure, Tach injects `ROLLBACK TO SAVEPOINT tach_test_start;`. This instantly reverts the database state to the snapshot taken at step 3, entirely in memory (assuming the transaction fits in the DB buffer pool), avoiding disk I/O.²¹

#### 4.2. Transparent Driver Interception

To make this seamless for legacy plugins, the test code cannot be required to manually manage transactions. Tach achieves transparency by hooking the database driver.

##### 4.2.1. PostgreSQL (Psycopg2) Hooks

For PostgreSQL, the psycopg2 library exposes a set_wait_callback hook. This was designed for coroutine libraries (like gevent) but is repurposed here for transaction control.

*   **Mechanism:** Tach registers a callback that intercepts the wait loop of the driver. This allows the runner to monitor the transaction state.
*   **Isolation Enforcement:** By wrapping the cursor.execute method, Tach ensures that any explicit COMMIT issued by the test code is intercepted and effectively ignored or converted into a RELEASE SAVEPOINT (for nested transaction simulation), preserving the outer transaction wrapper.²³

##### 4.2.2. MySQL Interception

For MySQL/MariaDB, the MySQLdb (mysqlclient) library is targeted. Since MySQL does not support nested transactions as gracefully as Postgres, the hook logic wraps the execute method to catch MySQLdb.Error. If a test crashes or fails, the wrapper explicitly issues a ROLLBACK to the connection handle before returning it to the pool. This prevents "dirty" connections from polluting subsequent tests.²⁵

### 5. Cross-Platform Architecture: The "Poor Man's Fork"

While Linux Namespaces provide the ideal substrate, Project Tach must support Windows and macOS. Neither OS supports fork(), the primitive required for cheap process cloning. The architecture implements platform-specific emulations of fork() using undocumented or specialized APIs.

#### 5.1. Windows: NtCreateUserProcess and Snapshotting

Windows process creation (CreateProcess) is slow because it involves the csrss.exe subsystem, console initialization, and rigorous DLL loader checks.

##### 5.1.1. NtCreateUserProcess Strategy

To bypass the Win32 subsystem overhead, Tach leverages the Native API syscall NtCreateUserProcess (exported by ntdll.dll).

*   **Mechanism:** This syscall creates a process kernel object with minimal user-mode initialization. By carefully constructing the PS_ATTRIBUTE_LIST, specifically the PsAttributeParentProcess, Tach can instruct the kernel to create a child process that inherits the handle table and address space traits of the parent.²⁷
*   **Performance:** This reduces process creation time from ~20-50ms (CreateProcess) to <10ms, approaching the performance of Linux fork().²⁷

##### 5.1.2. Process Snapshotting (PssCaptureSnapshot)

For state restoration, Windows 8.1 introduced the Process Snapshotting API.

*   **PssCaptureSnapshot:** This API allows capturing the state of a running process. Internally, it uses the OS's memory manager to mark the process's pages as Copy-on-Write (CoW).
*   **Restoration Flow:** Tach creates a "Template" process that initializes the environment (loads Python, imports modules). It then takes a snapshot handle using PssCaptureSnapshot. For each test, it spawns a clone from this snapshot. The clone shares physical memory with the template until it writes to it, maximizing memory efficiency and startup speed.²⁹

##### 5.1.3. Filesystem Redirection via Detours

Since Windows lacks mount namespaces, filesystem isolation is achieved via API hooking using Microsoft Detours.

*   **Detour Function:** Tach injects a DLL that detours CreateFileW, DeleteFileW, and NtCreateFile.
*   **Path Rewriting:** The detour function intercepts the file path. If the path refers to a protected resource (e.g., the project source root), the function rewrites the path to point to a temporary sandbox directory (e.g., C:\Temp\Sandbox_123\src) before calling the original kernel function. This effectively virtualizes the filesystem in user space.³¹

#### 5.2. macOS: Mach VM Remapping and SIP Evasion

macOS poses strict security challenges due to System Integrity Protection (SIP) and the hardened runtime.

##### 5.2.1. vm_remap for Fast Cloning

The Mach microkernel provides the vm_remap function, which maps a range of memory from one task (process) to another.

*   **Mechanism:** To simulate fork(), the runner spawns a suspended process (using posix_spawn with POSIX_SPAWN_START_SUSPENDED). It then iterates through its own memory regions and uses vm_remap to map them into the child's address space with Copy-on-Write protections.
*   **Result:** The child process "wakes up" with a memory layout identical to the parent, effectively cloning the state without the overhead of copying data.³³

##### 5.2.2. SIP and DYLD_INSERT_LIBRARIES

The standard interposition variable DYLD_INSERT_LIBRARIES is sanitized (ignored) by the macOS dynamic linker when running system binaries or signed code protected by SIP.

*   **Bypass Strategy:** To enable interposition for filesystem isolation, Tach cannot run directly against /usr/bin/python3 (which is SIP-protected). Instead, the architecture requires copying the Python binary to a user-writable directory (e.g., ~/.tach/python3). When executed from this location, the binary loses its platform-signed status, allowing DYLD_INSERT_LIBRARIES to function, permitting the injection of the interception library (the macOS equivalent of the LD_PRELOAD shim).³³

### 6. Advanced Isolation Horizons: eBPF and Library OS

For environments where security is critical (e.g., running untrusted third-party plugins), the Namespace/Detours approach may be insufficient. The architecture incorporates eBPF and Library OS technologies for defense-in-depth.

#### 6.1. eBPF Syscall Rewriting

Extended Berkeley Packet Filter (eBPF) allows programmable logic to run within the kernel.

*   **Mechanism:** Tach attaches an eBPF program to the tracepoint/sys_enter_openat hook.
*   **Argument Rewriting:** Using the bpf_probe_write_user helper, the BPF program can modify the filename argument in the user-space memory of the calling process *before* the kernel acts on it.
*   **Application:** If a plugin attempts to open /etc/shadow, the BPF program detects the pattern and overwrites the buffer with /dev/null or a dummy file path. This provides enforcement that is faster than ptrace (no context switch) and harder to bypass than LD_PRELOAD (kernel-level enforcement).³⁷

#### 6.2. Library OS: Gramine and gVisor

Library OSes virtualize the kernel interface itself, providing the strongest possible isolation.

##### 6.2.1. Gramine (SGX)

Gramine (formerly Graphene) allows running unmodified Linux binaries inside Intel SGX enclaves.

*   **Security:** This protects the test code not just from other processes, but from the host OS itself (Iago attacks).
*   **Trade-off:** The overhead is approximately 10-20% for computational tasks, but significantly higher for process creation due to the cost of enclave initialization and the lack of native fork support (emulated via slow checkpoint/restore).³⁸

##### 6.2.2. gVisor (Sentry)

gVisor intercepts syscalls and handles them in a user-space kernel (Sentry) written in Go.

*   **Python Performance:** Research indicates that gVisor imposes a 2-4x latency penalty on Python module imports. This is due to the "thundering herd" of stat and open calls Python makes during startup, each of which must pass through the Sentry's VFS layer.
*   **Optimization:** To make gVisor viable, Tach employs a "Zipimport" strategy. By bundling the entire test environment into a single .zip file, the number of filesystem metadata operations is drastically reduced, mitigating the VFS bottleneck.⁷

### 7. Performance Analysis and Overhead Modeling

The following analysis quantifies the expected overhead of each architectural component, informing the adaptive selection logic of the Tach runner.

#### 7.1. Filesystem Virtualization Overhead

| Mechanism | Operation Cost | Context Switches | Throughput Impact |
| :--- | :--- | :--- | :--- |
| Namespaces | Native (Kernel) | 0 | < 1% |
| Seccomp-BPF | Filter Eval (~100ns) | 0 (Pass) / 2 (Trap) | ~15% (Mixed I/O) |
| Ptrace | Signal + Wait (~5µs) | 2 per syscall | > 100% |
| LD_PRELOAD | Function Pointer (~5ns) | 0 | Negligible* |

*\*Note: LD_PRELOAD overhead is low but isolation is flawed.*

#### 7.2. Process Creation Latency

| Platform | Mechanism | Latency (ms) | Scaling Factor |
| :--- | :--- | :--- | :--- |
| Linux | clone(CLONE_NEWNS) | < 0.5ms | O(1) (CoW) |
| Windows | NtCreateUserProcess | ~5-10ms | O(1) |
| Windows | CreateProcess (Std) | ~20-50ms | O(DLLs) |
| macOS | vm_remap (simulated fork) | ~2-5ms | O(Memory Regions) |
| gVisor | Sandbox Creation | ~150ms | O(Sentry Init) |

#### 7.3. Data Transport Throughput

| Method | Serialization | Throughput (GB/s) | CPU Usage |
| :--- | :--- | :--- | :--- |
| Pipe (Pickle) | Yes (Heavy) | ~0.5 GB/s | High |
| Shared Mem (Raw) | No | ~15 GB/s | Low |
| PyArrow (Zero Copy) | No | > 20 GB/s | Negligible |

### 8. Implementation Roadmap

**Phase 1: The Core (Linux)**
*   Implement the Rust-based Namespace runner using the nix crate.
*   Develop the unshare logic to establish private Mount and User namespaces.
*   Create the Seccomp filter generator to trap dangerous syscalls when namespaces are unavailable.

**Phase 2: The Bridge (Python)**
*   Build the PyO3 bindings for the runner.
*   Implement the Apache Arrow shared memory transport layer.
*   Develop the sys.modules scrubber and pytest global-reset fixture.

**Phase 3: The Adapters (Windows/macOS)**
*   **Windows:** Implement the NtCreateUserProcess harness and the Detours DLL for CreateFileW interception.
*   **macOS:** Implement the posix_spawn + vm_remap cloning logic and the DYLD_INSERT_LIBRARIES injector.

**Phase 4: The Shield (Security)**
*   Integrate bpf_probe_write_user for high-performance path rewriting.
*   Add support for gVisor runtime configuration for untrusted workloads, incorporating the Zipimport optimization to mitigate startup latency.

---

### 9. Conclusion

The architectural blueprint for Project Tach creates a system that rivals the performance of local execution while providing the safety guarantees of containerization. By prioritizing native kernel primitives—Namespaces on Linux, NtCreateUserProcess on Windows, and vm_remap on macOS—the "Linux Core" eliminates the overhead of traditional virtualization. The integration of PyO3 with Zero-Copy Arrow transport resolves the historic bottleneck of cross-language testing, while the Savepoint Injection strategy transforms database testing from an I/O-bound to a memory-bound operation. This comprehensive design positions Project Tach as a next-generation runtime capable of executing massive, polyglot test suites with sub-millisecond precision.
